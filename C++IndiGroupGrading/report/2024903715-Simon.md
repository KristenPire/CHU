## Overall

"Last Train: Lost Property" is a moody three-stage RPG set in an empty station at 00:43 — Mina, the last staff member on duty, works through Platform, Tunnel, and Last Carriage fighting spectral remnants to recover a missing suitcase. The game has a consistent atmospheric voice, a three-way outcome system, and an `Encounter` struct design that separates data from logic cleanly. The main deductions are a too-large `playEncounter()` function, a handful of magic numbers, and missing `override` keywords in the subclass declarations.

## Bonus

**Bonus score: 8 / 10**

The atmospheric setting is the strongest thing here. A 00:43 shift at a closed station, three locations that each feel distinct (the blinking lights on Platform, the wet rails in the Tunnel, the dead train at Last Carriage), and a narrative voice for Mina that stays consistent: "That wasn't a passenger... not anymore." Most submissions in this batch have enemies that could be from any game. Yours fit the world.

The `Encounter` struct (Game.hh:17-28) is the standout architectural choice: every encounter is a complete data record — location, intro text, enemy, victory line, reward, story lines. `run()` and `playEncounter()` operate on that data without knowing the specifics of each fight. Adding a fourth encounter means adding one more struct literal in the constructor; zero logic changes needed. That's real design thinking.

The free-turn item mechanic (choice 2 calls `continue` at Game.cpp:180, skipping the enemy's turn) is a small but meaningful game design decision — using an item is a genuine tactical option rather than just another action that costs a turn, which adds real weight to the Flashlight and Old ID Card pickups mid-combat.

**Clean Code note:** The codebase is genuinely clean — consistent naming convention, focused helpers, `run()` that reads like a game design doc. The one thing that would make it excellent is breaking `playEncounter()` into `resolvePlayerTurn()` and `resolveEnemyTurn()` helpers. It's currently 83 lines doing too many things; the same care shown in `run()` and the supporting helpers should apply there too. Named constants for the defend bonus and damage swing would also help with future balance tuning.
