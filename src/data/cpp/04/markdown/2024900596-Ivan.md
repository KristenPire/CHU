**Inheritance — 7 / 10**

- **Non-virtual Entity methods** (−1 design, −1 technical) — Character and Enemy re-declare methods via name hiding, not override; no polymorphic dispatch possible via Entity*

  Non-virtual methods on a base class mean that calling `getName()` through an `Entity*` always invokes `Entity::getName()` regardless of the actual object type — the derived class's override is ignored, and you cannot use a container of `Entity*` to uniformly operate on Characters and Enemies.

  ```cpp
  // Entity.hh — all methods are non-virtual; hiding, not overriding
  class Entity
  {
  public:
      Entity(const std::string& name, int hp, int atk, int def);
      std::string getName() const;   // non-virtual
      int         getHP()   const;   // non-virtual
      bool        isAlive() const;   // non-virtual
      void        takeDamage(int amount);  // non-virtual
      // no virtual ~Entity()
  };
  ```

- **No virtual destructor on Entity** (−1) — Entity* could in principle delete derived objects unsafely

  Without `virtual ~Entity()`, deleting a Character through an Entity pointer will only run Entity's destructor — any resources owned by Character will leak, and if Character ever adds dynamic members, this becomes a real bug.

  ```cpp
  // Entity.hh — no virtual destructor; deletion through Entity* is unsafe
  class Entity
  {
  public:
      Entity(const std::string& name, int hp, int atk, int def);
      // ... no virtual ~Entity() ...
  ```

- **No `override` keyword** (−1) — Entity's methods are non-virtual, so there is nothing to override

  When re-declaring a non-virtual base class method in a derived class, adding `override` would have caused a compile error and revealed the design issue early — omitting it means the shadowing went undetected.
