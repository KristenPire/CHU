- **`battle()` monolith** (−3) — 51 lines mixing display, input, four-case player action dispatch, and enemy-turn logic without helper extraction

  Mixing display, input, combat resolution, and enemy-turn in a single loop means a change to how the enemy attacks also requires reading past all the player-side code to find it — each concern should be a named function.

  ```cpp
  // source/Game.cpp:221-263 — battle() mixes all concerns

      while (hero.isAlive() && enemy.isAlive()) {
          defending = false;
          showStatus();           // display mixed in
          int c;
          if (!readIntOrExit(c, "...")) exit(0);  // input handling
          if (c == 3) defending = true;
          if (c == 2) useItemMenu(&enemy);         // item action
          if (c == 1) { /* attack resolution */ }  // combat
          // enemy turn inline at the end
          int dmg = enemy.getATK() - hero.getDEF();
          hero.takeDamage(dmg);
      }
  }
  ```

- **Naming issues** (−5) — `using namespace std;` at file scope (Game.cpp:9); `#define` macros for ANSI color codes instead of `constexpr`; `inv`, `c`, `d`/`dmg` as variable names; Dragon Sword stored as `Item::Type::Potion` (semantic mismatch); no namespace discipline

  `using namespace std` at file scope means every `std::` name silently becomes available everywhere in the translation unit — a name collision with a local variable or function is a hard-to-diagnose bug.

  ```cpp

  using namespace std;

  #define RESET   "\033[0m"
  #define RED     "\033[31m"
  #define GREEN   "\033[32m"

  // source/Game.cpp:269 — Dragon Sword stored as Potion type
  inv.addItem(Item("Dragon Sword", Item::Type::Potion, 0));
  ```

- **`exit(0)` on death and invalid input** (−4) — abruptly terminates, bypasses RAII cleanup; Character-reconstruction pattern for stat modification in `levelUp()` and `jeanneSecondDialogue()` is fragile

  Calling `exit(0)` bypasses the entire C++ stack unwinding — destructors do not run, open files may not be flushed, and any RAII cleanup the program depends on is silently skipped.

  ```cpp

  if (!hero.isAlive()) {
      cout << RED << "YOU DIED\n" << RESET;
      exit(0);   // destructors skipped, RAII cleanup never runs
  }

  // source/Game.cpp:148-153 — stat modification via Character reconstruction

      hero = Character(hero.getName(), hero.getMaxHP() + 10,
                       hero.getATK() + 5, hero.getDEF() + 5);
      hero.heal(oldHP + 10);  // fragile — depends on remembering to carry HP over
  }
  ```

  An `operator<<` for Character that omits ATK and DEF means `std::cout << hero` never shows the stats that determine combat outcome — the operator is present but not useful for displaying combat state.

  ```cpp
  {
      os << c.name << " HP: " << c.hp << "/" << c.maxHp;
  ```

- **`operator<<` on Item** (−1) — prints "name (+value)"; omits type string

  Without the type label, a player looking at "Dragon Sword (+0)" or "Explosion Potion (+50)" in the inventory has no way to know what kind of item each one is from the display alone.

  ```cpp
  // source/Item.cpp:16-19 — no type string in output
  std::ostream& operator<<(std::ostream& os, const Item& item)
  {
      os << item.getName() << " (+" << item.getValue() << ")";
      return os;
  }
  ```

- No bonus overloads (−2)

  Two additional points were available for any operator that fits naturally in your code — `operator+=` for healing, `operator-=` for damage, `operator<` for comparing item values, or `operator+` for merging inventories are all common choices in an RPG.

**Heap / Dynamic Memory — 10 / 10**

**Inheritance — 0 / 10**

The Goblin, Undead, and Black Dragon each warrant distinct attack behavior — a `Character` base with `Goblin`, `Undead`, and `BlackDragon` subclasses each overriding a virtual `takeTurn(Character& target)` would replace the inline enemy-turn block in `battle()` with a single dispatch and make each enemy's behavior independently modifiable.
