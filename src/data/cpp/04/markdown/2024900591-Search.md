**Inheritance — 7 / 10**
- Entity captures shared state (name, HP, ATK, DEF) and behaviors (getters, isAlive, applyDamage); Character extends it with game-specific methods — a clean is-a relationship
- **No virtual destructor** (−2) — Entity.hh has no virtual destructor; technically undefined behavior if ever deleted via an Entity pointer

  If any code ever deletes a Character through an Entity pointer, the Character destructor will not run; with no `virtual ~Entity()`, the compiler cannot generate the correct vtable entry, and the behavior is undefined regardless of whether any destructors currently do meaningful work.

  ```cpp

      std::string getName() const;
      // ... getters, isAlive, applyDamage ...

      std::string name_;
      int hp_;
      int max_hp_;
      // no virtual ~Entity()
  };
  ```

- No virtual methods means the hierarchy serves code reuse rather than polymorphism (−1)

  Without any virtual methods, you cannot write a function that accepts an Entity& and calls overridden behavior — every caller must know the concrete type, which defeats the purpose of having an inheritance hierarchy.


## Bonus

And having four distinct item types (heal, attack buff, defense buff, enemy weaken) means players are making actual decisions rather than just spamming attack.

The named constants for heavy strike behavior are a genuinely good touch. Most people would have just buried those numbers in the logic and moved on.

**Clean Code note:** Search's clearest strength is consistent naming discipline throughout — every variable and member tells you exactly what it holds, from `heavy_strike_chance_percent` to `hero_hp_before_hit` to `ward_ointment_count`. The Entity/Character inheritance hierarchy is clean and purposeful, and the helper functions in the anonymous namespace are properly scoped. The main area to grow is decomposition: `playStage()` is doing a lot at once, and pulling the item-use dispatch out into its own `applyItem()` helper would make the function much easier to follow at a glance.
