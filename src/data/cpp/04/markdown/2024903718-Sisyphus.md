## Overall

A Darkest Dungeon-inspired two-chapter dungeon crawler with a resolve affliction system (Stable/Courage/Fearful/Paranoid/Hopeless/Brutal), poison/bleed/stress mechanics, six distinct enemies, and a full loot/town/camp structure between encounters. The architecture spans 60 files with dedicated controllers, catalogs, and item pools, and the naming discipline — 40+ named constants, trailing underscores throughout — is exceptional. The one weak spot is `operator<<` for Item printing only the item name despite a rich 10-field metadata system.

## Sections

**Subject Requirements — 30 / 30**

- Comprehensive README with full bestiary (HP/ATK/DEF/SPD), equipment tables with stat bonuses, 12 consumables with effects, and three explicit end states

**Clean Code — 38 / 40**
- Extraordinary decomposition across 60 files: `runEncounter()` is 5 lines, `setupEncounters()` is 3 lines; Controller classes (RoundController, TownController, CampController, LootController) each own their functional domain
- Outstanding naming: 40+ named constants in anonymous namespaces (`kDamageThresholdForStress`, `kCourageChance`, `kParanoidHealthLossDivisor`, etc.); precise method names throughout
- **`run()` at 75 lines** (−1) — mixes chapter intro rendering, encounter loop control, and ending screen selection; a `runChapters()` wrapper would reduce its length

  A top-level `run()` function that renders UI, drives the chapter loop, and selects the ending screen is harder to unit-test and extend than one that simply calls focused helpers for each concern.

  ```cpp
  // Game.cpp:100 — run() at 75 lines mixing chapter intro, encounter loop, and endings
  // The anonymous namespace above it shows the right instinct (named constants),
  // but the function body bundles three responsibilities that could each be a helper:
  constexpr int kStartingCampSupplies = 2;
  constexpr int kStartingGold = 24;
  constexpr int kDamageThresholdForStress = 5;
  // ... 40+ more constants, then run() handles everything from intro to game-over screen
  ```

- **Three committed build directories** (−1 style) — `build-mingw`, `build-ui-layout-check`, `build-ui-split-check` are a significant repository hygiene issue

  Build artifacts committed to a repository bloat clone size, pollute diffs, and make it harder for reviewers to find the actual source files — a `.gitignore` rule for `build*/` prevents this entirely.

  ```
  // Three directories at repo root that should be in .gitignore:
  build-mingw/
  build-ui-layout-check/
  build-ui-split-check/
  ```

**Operator Overloading — 7 / 10**
- `operator<<` (Character) and `operator==` (Item, comparing all 10 fields) both correct
- `operator<<` (Inventory) handles empty case and prints indexed items — full marks
- **`operator<<` (Item)** (−1) — prints only `item.getName()`; no type, value, or effect text despite rich item metadata; no bonus overloads

  With 10 fields of item metadata (buyPrice, effectText, atkBonus, etc.) faithfully stored, streaming an Item only as its name throws away all the information that makes items distinguishable in a player-facing display.

  ```cpp
  // Item.cpp:221 — operator<< discards all metadata and prints only the name
  std::ostream& operator<<(std::ostream& os, const Item& item)
  {
      os << item.getName();
      return os;
  }
  // Compare: operator== checks all 10 fields — the data is there, just not shown
  ```

**Heap / Dynamic Memory — 10 / 10**
- `ItemPtr = shared_ptr<Item>` used exclusively throughout: Inventory stores `vector<ItemPtr>`, Hero stores `ItemPtr equippedWeapon_`/`equippedArmor_`. Virtual destructors on both hierarchies. No raw owning pointers. Full marks.

**Inheritance — 10 / 10**
- Three-tier hierarchy: Character → Hero and Character → Enemy → {AshWolf, Ghoul, Cultist, BlessedOne, HeartOfNight, HollowKing}; Item → {WeaponItem, ArmorItem, PotionItem, 10 ConsumableItems}. Combat functions operate on `Character&` for polymorphic dispatch. Virtual destructor, `override` keyword, no object slicing. Full marks.

## Bonus

**Bonus score: 9 / 10**

The resolve system is the standout here — Courage, Fearful, Paranoid, Hopeless, Brutal each change how your character actually plays, and designing that into a student C++ project is genuinely impressive. The Pervitin crash mechanic and the adrenaline revival are exactly the kind of high-risk, high-drama moments that make combat feel like it matters.

The two-chapter structure with a town phase between them, rarity-split loot pools, and a full encounter catalog gives the whole thing real shape. It's atmospheric in a way that's hard to pull off in a terminal game.

**Clean Code note:** The codebase is beautifully organized — split across dedicated controllers (RoundController, TownController, CampController, LootController), catalogs, and item pools, with a consistent trailing-underscore naming convention throughout. The anonymous namespace in Game.cpp replacing every magic number with a named constant is a professional touch, and the use of `std::mt19937` and `shared_ptr<Item>` shows solid modern C++ awareness. The code is expressive enough that comments are rarely needed. It's the kind of codebase you'd actually enjoy reading.
