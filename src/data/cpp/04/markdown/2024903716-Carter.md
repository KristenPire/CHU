## Overall

A straightforward hero's adventure with a single enemy and all three required item types doing genuinely different things — the potion heals, the sword permanently raises attack, the armor raises defense. The decomposition is clean and the code is easy to follow. The main weaknesses are Windows-only platform code that introduces a 2-second delay every round, severely unbalanced combat numbers, and no inheritance.

## Sections

**Subject Requirements — 27 / 30**
- All five required classes fully implemented; all 3 item types functional; 3 distinct end conditions (win/lose/flee)
- **CMakeLists.txt location** (−1) — Found at `project/CMakeLists.txt`, not at repo root

  Standard tooling and graders expect `CMakeLists.txt` at the repo root; placing it in a subdirectory means `cmake .` from the cloned repo root fails with no CMakeLists.txt found.

  ```
  # repo root — no CMakeLists.txt here
  project/
    CMakeLists.txt   ← found here instead
    Character.cpp
    Game.cpp
  ```

- **README detail** (−2) — Game description is generic ("A hero goes on an adventure against dangerous enemies"); no enemy names or stats listed at all

  A README without enemy names or item values gives players and reviewers no information about what to expect from the game and makes it impossible to verify game balance at a glance.

**Clean Code — 31 / 40**
- Excellent decomposition: `run()` (5 lines), `playerAttack()` (2 lines), `enemyAttack()` (2 lines), `flee()` (8 lines), `battleLoop()` (~18 lines clean switch dispatch)
- No `using namespace std` anywhere
- **`useItem()` dispatch** (−2) — Uses three sequential `if` statements instead of `else if` or `switch`; using an item skips the enemy counter-attack while attacking does not (inconsistent turn handling)

  Sequential `if` statements on mutually exclusive conditions mean all three branches are always evaluated, and if multiple branches could fire (they cannot here, but the structure implies they might) the result is silently wrong behavior.

  ```cpp
  // Game.cpp:84 — three separate ifs instead of else-if or switch
  if (used.getType() == Item::Type::Potion) {
      hero.heal(used.getValue());
  }
  if (used.getType() == Item::Type::Weapon) {
      hero.addAttack(used.getValue());
  }
  if (used.getType() == Item::Type::Armor) {
      hero.adddefense(used.getValue());
  }
  // Note: battleLoop() calls enemyAttack() after attack but not after useItem()
  ```

- **Naming inconsistency** (−2) — No member naming convention; `adddefense` (lowercase d) vs `addAttack` (uppercase A) in the same class

  Inconsistent capitalisation within the same class forces callers to remember which convention applies to each method, and makes the API feel unfinished.

  ```cpp
  // Game.cpp:89-94 — addAttack vs adddefense in the same useItem() block
  hero.addAttack(used.getValue());   // uppercase A
  // ...
  hero.adddefense(used.getValue());  // lowercase d — inconsistent
  ```

- **Platform code** (−4) — `#include <Windows.h>` with `system("cls")` and `Sleep(2000)`; the 2-second sleep in `printStatus()` adds a mandatory delay every combat round; `takeDamage()` allows 0 damage (no minimum 1)

  Code that calls Windows-only APIs will fail to compile on any Linux or macOS machine — including the grader's — and a 2-second forced sleep makes a game actively unpleasant to play.

  ```cpp
  // Game.cpp:5 — Windows-only header
  #include<Windows.h>

  // Game.cpp:30 — mandatory 2-second pause before every status display
  void Game::printStatus() {
      Sleep(2000);
      system("cls");
      // ...
  }
  ```

**Operator Overloading — 8 / 10**

- No bonus overloads

**Heap / Dynamic Memory — 9 / 10**
- All state stored by value; no raw owning pointers; no `new`/`delete` anywhere
- Minor deduction: no opportunity to demonstrate polymorphic heap management (no inheritance hierarchy) (−1)

**Inheritance — 0 / 10**
- Not used. Both hero and enemy are plain `Character` objects stored by value. An `Item` base class with `Potion`, `Weapon`, and `Armor` subclasses each overriding a virtual `apply(Character&)` would have replaced the three sequential `if` statements in `useItem()` with a single polymorphic call, and made adding new item types straightforward.

## Bonus

**Bonus score: 6 / 10**

All three item types actually do different things — the potion heals, the sword permanently raises your attack, the armor raises your defense. That's real strategic variety for a single-enemy game, and it's more than a lot of submissions managed.

"You coward!!! Escape successfully!!!" is a great line. It shows the game has a voice, which is harder to pull off than it looks.

**Clean Code note:** The decomposition is genuinely good — `run()` is 5 lines, the battle loop delegates cleanly to `playerAttack()`, `enemyAttack()`, `flee()`, `useItem()`, and `checkWinLose()`, and each of those is short and focused. No `using namespace std` anywhere, which is a discipline many students skip. The one rough edge is the inconsistency between `addAttack` and `adddefense` (uppercase A vs lowercase d in the same class) — it reads like one was written before the other without a second look. Overall though, this is tidy code that's easy to read through.
