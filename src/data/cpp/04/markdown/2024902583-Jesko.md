**Heap / Dynamic Memory — 7 / 10**
- Game owns six raw pointer members; all correctly deleted in `~Game()`. Operator owns `vector<ItemEffect*>`; all deleted in `~Operator()`.
- **Rule of Three violated** (−3) — Game defines `~Game()` but no copy constructor or copy-assignment; Operator same; any accidental copy of either class would double-free all owned pointers

  A class with a destructor that deletes raw pointers must also define a copy constructor and copy-assignment operator — otherwise the compiler-generated ones perform a shallow copy, and when both copies are destroyed, the same pointers are deleted twice, corrupting the heap.

  ```cpp
  // Game.hh:28-43 — six raw pointer members, destructor defined, no copy ctor/assign
  Operator* operator_;
  Doctor* doctor_;
  SpellManager* spellManager_;
  ItemManager* itemManager_;
  Shop* shop_;
  Enemy* currentEnemy_;
  // ~Game() correctly deletes all six, but Game(const Game&) and operator= are missing
  ```

**Inheritance — 9 / 10**
- Abstract `Spell` → `FortifySpell`, `SleightSpell`, `BloodbathSpell`, `FocusSpell`, `BreachSpell`, `SwiftSpell`; pure virtual `cast(Operator&, Enemy&)` dispatched by SpellManager every time the player uses Defend — runtime polymorphism genuinely drives combat
- Virtual destructor on Spell; `override` used correctly on all six subclasses
- **Minor deduction** (−1) — derived spell classes each define explicit `~FortifySpell() {}` etc. rather than `= default` or `override`; suggests a conceptual gap about virtual destructor chains

  Defining an explicit empty destructor in a derived class is redundant when the base already has a virtual destructor — the compiler generates the correct one automatically, and writing it explicitly without `= default` or `override` suggests uncertainty about how destructor inheritance works.

  ```cpp

  public:

  ```
