  When the input dispatch, player action, enemy retaliation, and all three outcome branches all live in one function, a bug in the flee path requires understanding the attack path first — the concepts are entangled even though they don't depend on each other.

          else if (choice == 2) { useItem(); }

- **Ghost method** (−1) — `handleChoice()` declared in Game.hh:14 but never implemented; the logic was left inline in `run()` instead of being moved there — indicates an incomplete refactoring

  A method declared in a header but with no definition compiles only because it is never called — the moment any code calls it, it becomes a linker error; it also misrepresents the class interface to anyone reading the header.

  ```cpp
  // Game.hh:14 — declared but never defined anywhere
  class Game
  {
  public:
      Game();
      void run();
  private:
      void printStatus();
      void handleChoice();   // no implementation exists
      void useItem();
      Character* _player;
      Character* _enemy;
      Inventory  _inventory;
  };
  ```

**Heap / Dynamic Memory — 7 / 10**
- Uses raw `new Character(...)` for `_player` and `_enemy`; Inventory uses raw `new std::vector<Item>()`

- **No Game destructor** (−2) — if Game is destroyed before `run()` completes, `_player` and `_enemy` leak; RAII is violated

  RAII means a resource's lifetime is tied to its owning object's lifetime; allocating in the constructor but only freeing inside `run()` means any exception or early destruction before `run()` finishes leaves both Character objects leaked with no recovery path.

  ```cpp
  // Game.cpp:57-58 — cleanup only happens at end of run()
      delete _player;
      delete _enemy;
  }   // but Game has no ~Game() destructor
  // If Game is destroyed before run() completes, both pointers leak
  ```

- **Unnecessary heap allocation** (−1) — `new std::vector<Item>()` is pointless indirection; a value member is simpler and safer

  Heap-allocating a vector adds Rule of Three complexity (copy ctor, copy-assign, destructor all written manually) for zero benefit — the vector already manages its own heap memory internally.

  ```cpp
  // Inventory.cpp:3-4 — vector allocated on heap for no reason
  Inventory::Inventory() {
      _items = new std::vector<Item>();
  }
  // Compare to the simpler alternative: just declare std::vector<Item> _items;
  ```

**Inheritance — 0 / 10**

This would also make it natural to give `Goblin` its own attack logic without inlining it in `run()`.
