## Overall

A dungeon adventure with random exploration events — traps, treasure chests, a mysterious trader, rest sites — and a final boss gated behind a progression counter. **Clean Code — 32 / 40**
- Outstanding use of k-prefix named constants in anonymous namespace (Game.cpp:11-26) — almost no magic numbers in logic code
- Strong decomposition: `showBattleHeader()`, `showTurnStatus()`, `handleEnemyLoot()`, `handleKristenVictory()` are clean, single-purpose helpers; `panelRow()` and `inventorySummary()` are well-named anonymous-namespace helpers
- **Canonical Form** (−3) — `Game` owns a raw `Character* hero`; no copy constructor, copy-assignment, or destructor defined — Rule of Three violated; hero is freed in `run()` rather than a destructor, so it leaks if `run()` is skipped

  A class that owns a raw pointer but lacks a destructor will leak memory whenever the object is destroyed before the owning method runs — an exception or early return is all it takes.

  ```cpp
  // Game.cpp:158 — hero deleted in run(), not in a destructor
  if (!hero->isAlive()) cout << "\nYOU DIED. GAME OVER." << endl;
  delete hero;
  // hero is not set to nullptr; no destructor to catch the case where run() exits early
  ```

- **Comma-operator one-liners** (−2) — `handleEnemyLoot()` uses the comma operator to chain a `cout`, `addItem`, and increment into single statements, making the logic harder to read

  Packing multiple side effects onto one line via the comma operator means a reader must parse the entire expression to understand what happens — a future maintainer editing one branch is likely to miss that two or three things happen there.

  ```cpp
  // Game.cpp:264-266 — each branch chains cout + addItem (+ increment) via comma operator
  if (loot == 0) cout << enemyName << " dropped a Healing Potion!" << endl, inventory.addItem(Item("Healing Potion", Item::Type::Potion, 15));
  else if (loot == 1) cout << enemyName << " dropped a Dagger!" << endl, inventory.addItem(Item("Dagger", Item::Type::Weapon, 2)), baseAttack += 2;
  else cout << "No extra loot this time." << endl;
  ```

**Operator Overloading — 5 / 10**
- `operator<<` on Inventory is correct — comma-separated list of item names, handles empty correctly
- **Incomplete Character operator<<** (−1) — Character.cpp:38 prints name and HP/maxHP only; ATK and DEF omitted

  Omitting ATK and DEF from the output means you can't use `operator<<` to display a full character stat sheet — callers must reach into the object's getters separately, defeating the purpose of the operator.

  ```cpp
  // Character.cpp:38 — operator<< only outputs two of four stats
  std::ostream& operator<<(std::ostream& os, const Character& c) {
      os << c.getName() << " | HP: " << c.getHP() << "/" << c.getMaxHP();
      return os;
      // ATK: c.getATK() and DEF: c.getDEF() never printed
  }
  ```

- **Incomplete Item operator==** (−1) — Item.cpp:18 compares only `name_`; missing type comparison means a potion and sword with the same name would compare equal

  An equality operator that ignores type and value will produce false positives — two items that are semantically different (a Potion and a Weapon both named "Iron") will be treated as the same item in any container search or duplicate check.

  ```cpp
  // Item.cpp:18 — only name is compared; type and value ignored
  bool Item::operator==(const Item& other) const {
      return name == other.name;
  }
  ```

- **Incomplete Item operator<<** (−1) — Item.cpp:22 prints name only; type and value omitted

  Printing only the name makes it impossible to distinguish a "Health Potion (Potion, +15)" from a "Health Potion (Weapon, +0)" at a glance — the output provides no actionable information beyond what `getName()` already gives.

  ```cpp
  // Item.cpp:22 — operator<< outputs name only
  std::ostream& operator<<(std::ostream& os, const Item& item) {
      os << item.getName();
      return os;
  }
  ```

- No bonus overloads (−2)

  Two additional points were available for any operator that fits naturally in your code — `operator+=` for healing, `operator-=` for damage, `operator<` for comparing item values, or `operator+` for merging inventories are all common choices in an RPG.

**Heap / Dynamic Memory — 8 / 10**
- Raw pointer mode: `hero = new Character(...)` in `createHero()`; `delete hero` in `run()` — the pair matches
- **Dangling pointer** (−1) — `hero` not set to `nullptr` after deletion, leaving it dangling for the rest of `run()`'s stack frame

  Reading or writing through a dangling pointer is undefined behaviour; setting it to `nullptr` immediately after deletion ensures any accidental access fails loudly with a null dereference rather than silently corrupting memory.

  ```cpp
  // Game.cpp:158 — delete without nulling the pointer
  delete hero;
  // hero still holds the old address; any code that checks hero != nullptr will incorrectly believe it is valid
  ```

- **Rule of Three** (−1) — no copy constructor or copy-assignment on `Game`; any copy would double-free hero (though `Game` is never copied in practice)

  Without a copy constructor, if `Game` is ever passed by value or copied by accident, both the original and the copy will call `delete hero` on the same pointer — the second deletion is undefined behaviour that can corrupt the heap.

  ```cpp
  // Game.hh:29 — raw pointer member with no copy constructor or copy-assignment
  Character* hero;
  // No Game(const Game&), no Game& operator=(const Game&), no ~Game()
  ```

**Inheritance — 5 / 10**
- Enemy inherits from Character — a valid is-a relationship conceptually
- **Hollow subclass** (−3) — Enemy adds zero behavior: the entire class body is a single constructor forwarding to Character; no additional methods, no data, no virtual interface — provides no practical benefit over using Character directly

  A subclass that contributes nothing beyond its constructor gives the compiler no information to use for polymorphic dispatch — you incur the conceptual overhead of an inheritance hierarchy without gaining any of its benefits.

  ```cpp
  // Enemy.cpp:3 — entire implementation is a constructor forward
  Enemy::Enemy(const std::string& name, int hp, int atk, int def)
      : Character(name, hp, atk, def) {}
  ```

- **No virtual destructor** (−2) — Character has no virtual destructor; UB if Enemy were deleted via Character pointer

  Deleting a derived object through a base-class pointer without a virtual destructor only calls the base destructor — any resources the derived class manages are never freed, and the behaviour is officially undefined.

  ```cpp
  // Character.cpp — no virtual destructor declared in the base class
  // If code ever does: Character* p = new Enemy(...); delete p;
  // only ~Character() runs, not ~Enemy() — undefined behaviour
  ```

## Bonus

**Bonus score: 10 / 10**

Naming the final boss "Kristen" and the regular enemies after classmates is a genuinely funny choice that makes the game memorable in a way that no amount of polish can substitute for. The random-event exploration — traps, treasure chests, a mysterious trader, rest sites — creates real variety between fights and makes the dungeon feel alive rather than just a series of combat screens.

Gating the boss behind a progression counter instead of just throwing her at the player immediately is a solid structural instinct. It gives the game shape.

**Clean Code note:**
Echo's strongest habit is the consistent use of named constants — the full set of k-prefixed values in the anonymous namespace means there are almost no magic numbers floating around in the logic code, which makes the intent clear throughout. The decomposition into focused helpers like `showBattleHeader`, `showTurnStatus`, `handleEnemyLoot`, and `handleKristenVictory` is also genuinely good practice. The main things to tighten up are the comma-operator one-liners in `handleEnemyLoot` (which pack too much onto one line) and the incomplete operator implementations for Item — but the overall structural quality is solid.
