## Overall

A survival RPG on a deserted island with three genuinely different endings — death, rescue, or staying permanently — and a weather system that keeps each day feeling unpredictable. - **Interface deviations** (−4) — `heal()` renamed `addHP()`, `takeDamage()` renamed `hurt()`, `run()` renamed `runGame()`, `size()` renamed `getSize()`, `isEmpty()` renamed `empty()` — these all deviate from the required spec interface

  When methods are renamed away from the spec, any automated test harness or code that depends on the standard interface will fail to compile — the class cannot be used interchangeably with other implementations.

  ```cpp
  // Character.hh:25 — spec requires heal(), not addHP()
  void addHP(int num);
  // Enemy.hh:22 — spec requires takeDamage(), not hurt()
  void hurt(int dmg);
  // Game.hh — spec requires run(), not runGame()

  ```

- **Incomplete Item operators** (−2) — `operator==` compares only `itemName`, ignoring type and value; `operator<<` prints only `itemName`

  An equality check that ignores type and value will treat a Potion named "Apple" as equal to a Weapon named "Apple", causing silent logic errors whenever items are searched, compared, or removed by value.

  ```cpp
  // Item.cpp:14 — only itemName checked; type and value ignored
  bool Item::operator==(const Item& other) const {
      if (itemName == other.itemName)
          return true;
      return false;
  }
  // Item.cpp:21 — only itemName printed; type and value lost
  std::ostream& operator<<(std::ostream& out, Item& i) {
      out << i.itemName;
      return out;
  }
  ```

**Inheritance — 0 / 10**
- Not used. `Enemy` duplicates `Character`'s entire data layout and behavior (`name`, `hp`, `atk`, `def`, `isAlive()`) — making `Enemy` a subclass of `Character` and overriding only `hurt()` with its island-specific damage calculation would have eliminated the duplication and let `battle()` take a single `Character&` parameter instead of maintaining two separate combat paths.

  When Enemy and Character evolve separately, any change to shared behavior (e.g., how damage is clamped, how alive-status is computed) must be made in two places, and they will inevitably drift out of sync.

  ```cpp
  // Enemy.hh:5 — parallel structure to Character with no inheritance

  private:
      std::string name;
      int hp;
      int atk;
      int def;
  public:
      bool isAlive() const;
      void hurt(int dmg);   // duplicates Character::takeDamage
  };
  ```

## Bonus

**Bonus score: 9 / 10**

Three genuinely different endings — die from hunger or thirst, get rescued by helicopter, or stay on the island forever — is a creative structure that most students don't attempt. The weather system is a nice touch: rain refills water, heat drains HP, wind nerfs stats, so each day feels unpredictable rather than routine.

The scout mechanic on days 3, 6, and 9 forcing you into the forest adds real tension to the area loop, and the wood-gathering-to-crafting progression gives the 10 days a satisfying arc.

**Clean Code note:**
The helper decomposition here is genuinely good — almost every action in the game (`weatherEffect`, `collectResources`, `craftItem`, `buildSOS`, `battle`) has its own focused function that stays under 40 lines. The `Inventory` class is clean and handles itself by value without any raw pointers, which is the right approach. Naming is functional throughout, though a few short variables (`op`, `b`, `c`) and the Windows-specific `system("pause")` calls stand out. The main thing to tighten up would be extracting the area-switch and item-use logic out of `runGame()` into their own helpers — the overall structure is already clearly pointing that direction.
