## Overall

A three-floor grid dungeon with a pressure mechanic that builds through exploration and triggers random debuffs — movement itself becomes a resource, which is a clever layer on top of standard RPG combat. The item combo system (Lemon Tea + Straw, King Sword + Crown + Armor) is a standout design touch that makes the inventory feel meaningful. The main gap is the absence of any inheritance hierarchy, and a few large functions that mix too many concerns.

**Clean Code — 34 / 40**

- Trailing-underscore naming consistent throughout; method names read as clear actions
- **generateMap() too large** (−3) — ~110 lines hardcoding all three floors inline; should be split into `generateFloor1/2/3()` helpers

  A 110-line function that hardcodes the layout of three different floors in sequential blocks means any change to floor 2 requires reading past all of floor 1's layout first — splitting into per-floor helpers makes each floor independently readable and modifiable.

  ```cpp
  // Game.cpp:60 — generateMap() hardcodes all three floors sequentially in one function
  void Game::generateMap(int floor) {
      if (floor == 1) { width_ = 5; height_ = 5; }
      else if (floor == 2) { width_ = 7; height_ = 7; }
      else { width_ = 9; height_ = 9; }
      // ... floor 1 tiles: Grunt, Bruiser, treasure, trap ...
      if (floor == 1) { setTile(1, 2, gruntTile); setTile(3, 1, bruiserTile); ... }
      else if (floor == 2) { ... }   // floor 2 continues for another ~40 lines
  ```

- **useItem() too large** (−3) — ~85 lines with a 14-case switch; deserves an `applyItemEffect()` helper

  A switch with 14 cases that each mix inventory manipulation, stat updates, and output in the same function body is difficult to extend — adding a 15th item requires understanding how all 14 existing cases are structured before knowing where to insert the new one safely.

  ```cpp
  // Game.cpp:294 — useItem() handles 14 distinct item effects inline
  void Game::useItem() {
      // ... input and inventory lookup ...
      switch (eff) {
          case Item::Effect::HealthPotion: hero_.heal(item.getValue()); used = true; break;
          case Item::Effect::Whiskey:      hero_.addPermanentATK(item.getValue()); used = true; break;
          case Item::Effect::ToiletPaper:  hero_.addPressure(-item.getValue()); used = true; break;
          // ... 11 more cases ...
      }
  ```

- **Style deductions** (−2) — unused private field `tempDefBonus_` (compiler warning); `addPressure(-value)` semantic mismatch; `// ADDED:` / `// MODIFIED:` annotation comments add clutter without aiding comprehension

  An unused private field generates a compiler warning on clean builds and indicates dead code that was planned but never connected — leaving it in suggests the design was partially abandoned mid-implementation.

  ```cpp
  // Character.hh:91 — tempDefBonus_ declared but never read or written after initialization
  int tempAtkBonus_;   // used in the whiskey item effect
  int tempDefBonus_;   // declared but never used — generates compiler warning

  // Game.cpp:324 — addPressure() called with negative to reduce pressure; misleading name
  hero_.addPressure(-item.getValue());   // semantically: "reducePressure(item.getValue())"
  ```

**Operator Overloading — 8 / 10**
- All four required operators correctly implemented: `operator<<` on Character and Item, `operator==` on Item, `operator<<` on Inventory
- No bonus operator overloads (−2)

**Heap / Dynamic Memory — 9 / 10**
- Inventory uses `std::vector<Item>*` — an unusual design, but canonical form is fully correct: `new` on construction, deep copy in copy-ctor and copy-assign (self-assignment guard), `delete` in destructor
- **Unnecessary heap allocation** (−1) — heap-allocating the vector adds implementation complexity for no semantic benefit; `std::vector<Item>` as a value member would be simpler and equally correct

  A `std::vector<Item>` value member gives you the same deep-copy behavior automatically (the compiler generates a correct copy constructor and destructor for free), whereas a raw pointer to a heap vector requires a manually written Rule of Three that is a source of potential bugs.

  ```cpp
  // Inventory.hh — raw pointer to heap-allocated vector
  private:
      std::vector<Item>* items_;   // requires new, deep copy in copy-ctor, delete in dtor
  // simpler equivalent: std::vector<Item> items_;  // Rule of Zero, no manual management
  ```

**Inheritance — 0 / 10**
- Not used. All classes are independent. An `Enemy` base with a virtual `attack(Character&)` — overridden by `Grunt`, `Bruiser`, and a `BossEnemy` subclass — would have let `Tile` store an `Enemy*` and dispatch combat without knowing the concrete type, replacing the flat `Character` approach used across all three floors.

## Bonus

The pressure mechanic that builds through exploration and triggers random debuffs is also a genuinely clever layer. It turns movement itself into a resource, which is hard to pull off.

**Clean Code note:** The overall structure is clean and the shorter helper functions (showMenu, showShop, checkItemCombos) are well-scoped. The main areas to improve are generateMap() at around 110 lines of hardcoded per-floor layout — splitting it into generateFloor1/2/3() helpers would help a lot — and useItem() with its 14-case switch, which deserves an applyItemEffect() helper. Naming is consistently strong with trailing underscores used throughout and descriptive method names that read as clear actions.
