- **Leading underscore risk** (−2 style) — leading underscore on private members (_name, _hp) is a reserved-identifier risk pattern and conflicts with the trailing underscore convention in Game.hh; combat() takes Enemy by value rather than by reference

  In C++, names beginning with an underscore followed by an uppercase letter, or two consecutive underscores, are reserved — using leading underscores on member names is one typo away from accidentally triggering undefined behavior with a compiler that accepts but misinterprets them.


  An `Enemy` subclass with no new methods is functionally identical to a `Character` — any code that uses `Enemy` could use `Character` directly, which means the inheritance adds no expressive power and no polymorphic capability.

The two-phase boss transformation is the highlight — the Eldritch Horror fully reassigning into an Awakened Horror at 20 HP rather than just bumping stats makes it feel like a real event. Framing the player's health as sanity and naming the lose condition "Sanity = 0" is the right call for a Lovecraftian game.

Random critical hits, damage variance, random loot between encounters — those details give the run real texture. The Story class keeping all narrative text separate is a good architectural instinct too.

**Clean Code note:** The three-file architecture (Game, Story, UI for narrative and display) is a strong design choice that keeps combat logic separate from storytelling. The inconsistency to address is the naming convention split: Game uses trailing underscore (_... wait, actually trailing: player_, hasFled_) while Character/Item/Inventory use leading underscore (_name, _hp) — unifying all private members to trailing underscore across all files would make the codebase feel coherent. Adding a virtual destructor to Character and giving enemies distinct subclasses (Cultist, DeepOne) would also make the inheritance design do more meaningful work.
