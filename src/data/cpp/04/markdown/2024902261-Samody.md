**Heap / Dynamic Memory — 8 / 10**
- Inventory `std::vector<Item*>` with Rule of Three; CharacterHero Rule of Three for inventory/armor/weapon pointers; Game deletes all Room* and player* in dtor
- **Game missing copy = delete** (−1) — no declared copy ctor/copy-assign; accidental copy would cause double-free

  Game owns `CharacterHero*` and four `Room*` members; if Game is ever copied (e.g., passed by value accidentally), the compiler-generated shallow copy will result in two Game objects sharing the same pointers — when both are destroyed, each pointer is deleted twice, causing undefined behavior.

  ```cpp
  // Game.hh — Game owns raw pointers but declares no copy constructor or copy-assignment
  class Game {
  private:
      CharacterHero* player;   // owned; deleted in ~Game()
      Room* room1;             // owned; deleted in ~Game()
      Room* room2, *room3, *room4;
  // missing: Game(const Game&) = delete; Game& operator=(const Game&) = delete;
  ```

- **BattleRoom/TreasureRoom raw pointers without explicit Rule of Three** (−1) — valid via virtual dtor chain but fragile

  Relying on the virtual destructor chain to correctly clean up subclass pointers works as long as the base class virtual destructor is always present and correct — but if a future refactor removes the virtual destructor or the override, the cleanup silently breaks with no compiler warning.

  ```cpp
  // Room.cpp:9 — BattleRoom deletes its enemy* in the destructor; no copy protection
  BattleRoom::~BattleRoom() { delete enemy; }
  // No copy constructor or copy-assignment declared: if a BattleRoom is copied,
  // two objects will share the same enemy pointer and both will delete it
  ```

**Inheritance — 9 / 10**
- Outstanding hierarchy: Character → CharacterHero/CharacterEnemy; abstract Room → BattleRoom/TreasureRoom/SpecialRoom; all dispatched polymorphically
- override keyword on CharacterEnemy::attackEnemy() and all Room::startEvent() subclasses; virtual destructors throughout; no object slicing
- **dynamic_cast in CharacterEnemy::attackEnemy()** (−1) — casts to CharacterHero* to add stress; a `virtual void addStress(int)` defaulting to no-op would eliminate the cast and preserve Liskov substitution

  Using `dynamic_cast` to access a derived class feature from a base class reference is a sign that the hierarchy is incomplete — it means CharacterEnemy has knowledge of CharacterHero's internals, creating tight coupling that makes future subclasses harder to add.

