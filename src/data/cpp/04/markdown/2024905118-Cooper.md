## Overall

A dungeon RPG with a two-hero choice (Luna vs. DarkBlue), ANSI colors, ASCII title art, HP bar progress display, and dramatic `sleep_for` pauses during combat — the presentation is genuinely polished. Dual inheritance hierarchies (Entity → Character, BaseItem → Item) and a dedicated UI/Colors class show real structural thinking. The main issues are neither Entity nor BaseItem having virtual methods, copy-pasted ASCII art across two functions, and boss identity determined by string comparison.

**Inheritance — 6 / 10**
- `Entity → Character` and `BaseItem → Item` — valid is-a relationships; provides code sharing for shared stats and name
- **No virtual methods on Entity or BaseItem** (−2 design) — Game stores enemies as `vector<Character>` (concrete type); no polymorphic dispatch; Goblin/Orc/Dark Lord cannot have different behaviors without string-comparing `getName()`

  Without virtual methods, a `Character*` or `Character&` cannot call enemy-specific behavior — every special case requires a string comparison on the name, which breaks silently if the name ever changes.

  ```cpp
  // Character.cpp:3 — Entity has no virtual methods at all
  Entity::Entity(const std::string& name, int hp, int atk, int def)
      : name(name), hp(hp), maxHp(hp), atk(atk), def(def) {}
  // No virtual attack(), no virtual onDefeat() — Goblin and Dark Lord are
  // behaviorally identical objects distinguished only by their name string.
  ```

- **No virtual destructor on Entity or BaseItem** (−1) — unsafe base class design

  If any code ever deletes a `Character` through an `Entity*` pointer, the `Character` destructor will not run, which is undefined behavior and can silently corrupt state.

  ```cpp
  // Character.cpp:3 — Entity constructor, no virtual destructor declared
  Entity::Entity(const std::string& name, int hp, int atk, int def)
      : name(name), hp(hp), maxHp(hp), atk(atk), def(def) {}
  // ~Entity() is implicitly non-virtual; ~Character() will be skipped
  // if deletion ever happens via Entity*
  ```

- **No `override` keyword** (−1) — Entity and BaseItem have no virtual methods; nothing to override

## Bonus

**Bonus score: 6 / 10**

The presentation here is genuinely polished — ANSI colors, ASCII title art, dramatic sleep_for pauses during combat, and an HP bar make this feel like a real game when you run it. Most projects skip all of that.

Luna vs. DarkBlue as a character choice right at the start is a good hook, and the "Coward!" flee ending is a satisfying third path that most people don't bother adding. The three-enemy escalation is clean and well-paced.

**Clean Code note:** The dual hierarchy (Entity → Character and BaseItem → Item) and the dedicated UI class with Colors namespace show real structural thinking. Named constants `MAX_DAMAGE_VARIATION` and `ATTACK_DELAY_MS` in place of magic numbers are a good habit. The main issue is that neither Entity nor BaseItem has virtual methods, so the inheritance is pure code sharing — storing enemies as `vector<Character>` means you can't give Goblin, Orc, and Dark Lord different behaviors without string-comparing on `getName()`, which is fragile. The copy-pasted ASCII art block in both `run()` and `selectHero()` is the most obvious duplication to clean up.
