- **levelStart() too large** (−2) — ~40 lines mixing level intro, inventory dispatch, skipBattle flag, battle invocation, and stone acquisition inline; separate activateStone() and awardStone() would reduce it to a clear dispatcher

  A function that both shows the level intro and decides whether to skip combat and awards the stone mixes presentation, control flow, and state mutation — making it hard to add a new stone effect without risk of breaking the level flow.

- **exit(0) for game-over** (−2 combined with style) — battle() calls exit(0) three times instead of returning a status code; abrupt termination bypasses cleanup and makes the function non-composable

  Calling `exit(0)` inside a library-level function like `battle()` means the function can never be tested in isolation, never be called in a context that wants to handle game-over gracefully (e.g. a "play again" loop), and never be composed with other logic — the calling code has no chance to respond.

  ```cpp
  // Game.cpp:76-82 — exit(0) called directly in battle()
      if (!thanos.isAlive() && !enemy.isAlive()) {

      }
      if (!thanos.isAlive()) {
          cout << "\nYou were defeated. Game Over.\n";
          exit(0);     // aborts again — no cleanup, no play-again
      }
  ```
