## Overall

A curse RPG with a 20-turn countdown forcing the player to fight through two escalating encounters to find the antidote. The Thief stealing turns instead of dealing damage is a clever mechanic, and the humor throughout — the elder eating the antidote, the Demon King's Switch complaints — gives the game a real personality. The main deductions are a missing inheritance section and structural readability issues (`goto` and string-based dispatch).

- **Function size and structure** (−4) — `run()` is 131 lines embedding two fights inline tied together with `goto victory` (Game.cpp:131, 152); `fight()` is 88 lines handling display, input, player action, enemy action, and curse in one loop

  A 131-line `run()` that embeds two full fight sequences inline cannot be read as a high-level flow — a reader must trace through all the combat code just to understand the game's overall structure, and any bug in one fight sequence requires scrolling through unrelated code to find it.

  ```cpp
  // Game.cpp:96-227 — run() embeds both fights and ties them with goto
  void Game::run() {
      // ... setup ...
      int result = fight(hero, thief, remainingTurns, inventory);
      if (result == 3) { gameWin = true; goto victory; }  // Game.cpp:131
      // ... loot, narrative ...
      result = fight(hero, demonKing, remainingTurns, inventory);
      if (result == 3) { gameWin = true; goto victory; }  // Game.cpp:152
      // ... 80 more lines ...
  victory:
      // ... victory handling ...
  }
  ```

- **Style issues** (−4) — `goto victory` for the win path is a significant readability issue; `enemyTurn()` and `useItem()` dispatch on enemy/item name strings (e.g. `if (enemy.getName() == "Thief")`) — fragile and unscalable; `const_cast<Inventory&>(inv)` in `displayCombatUI()` reveals a design mismatch; magic number 9999 as instant-kill in `useItem()`

  Dispatching on string names means a typo like `"thief"` instead of `"Thief"` silently produces wrong behavior with no compiler error — and adding a third enemy requires modifying `enemyTurn()` rather than just adding a new data source.

  ```cpp
  // Game.cpp:342-343 — enemy behavior dispatched by string comparison
  void Game::enemyTurn(Character& hero, Character& enemy, int& remainingTurns) {
  ```

**Inheritance — 0 / 10**
- Not used. The `enemyTurn()` string-dispatch (`if (enemy.getName() == "Thief")` / `"Demon King"`) is the direct cost of having no hierarchy — a `Character` base with `Thief` and `DemonKing` subclasses each overriding a virtual `takeTurn(Character& hero, int& remainingTurns)` would eliminate the fragile name comparison entirely and make adding a third enemy a matter of writing a new subclass.

## Bonus

**Bonus score: 8 / 10**

A curse that kills you over time and forces you to manage a 20-turn countdown across two fights is a genuinely distinctive premise — most games in this group don't think about tension at that level. The Thief stealing turns instead of just dealing damage is clever and fits the theme perfectly.

The humor throughout is the best part: the elder eating the antidote in front of you, the Demon King crying that his mother won't let him play Switch, the inventory-empty response of "Emperor's New Clothes." This game has a real personality.

**Clean Code note:** The visual presentation is solid — the `healthBar()` and `drawLine()` helpers produce clean ASCII combat panels, and the `m_` prefix convention is applied consistently throughout. The copy-and-swap idiom in Inventory's copy-assignment is genuinely exception-safe and correct. The main structural issues to address are the `goto victory` for the win path (which should be a function call or a loop flag), and the `enemyTurn()` dispatch by string comparison — giving each enemy a type enum or virtual method would make that code much more robust and extensible.
