## Overall

A dark plague-fantasy RPG with five named enemies, a forest camp hub, and a boss called the Red Death — Latin's game has genuine texture and holds together from the opening title to the final fight. ## Sections

**Subject Requirements — 30 / 30**

- README covers world overview, module responsibilities, gameplay rules, and encoding notes (10.4 KB)
- Three enemies plus two boss encounters; Smoke Potion skips an enemy turn — genuine item variety

**Clean Code — 37 / 40**
- Exceptional decomposition across nine source files; Fight::start() is 26 lines and focused on turn order only
- `FightState` struct bundles all fight references for helper functions — sophisticated architecture
- `battlePotionName()` (Fight.cpp:11) dispatches by raw item name strings — fragile; if item names change, the labels break silently
- **Inconsistent enum capitalization** (−1) — `Item::Type::material` uses lowercase while `Item::Type::Potion` uses PascalCase

  Inconsistent enum case means a reader cannot predict the correct spelling from convention, and a `switch` statement that adds new enum values must track two different capitalization rules.

  ```cpp
  // Item.cpp:85 — lowercase 'material' vs PascalCase 'Potion' in the same enum
  const Item forestFang("Forest Fang", Item::Type::material, 8, 1);
  const Item smallPotion("small Hp potion", Item::Type::Potion, 15, 1, 20, Item::Effect::Heal);
  // Item::Type::material and Item::Type::Potion exist in the same enum
  ```

- **`operator<<` for Inventory** (−2) — prints only "Inventory size: N"; not useful for display; actual inventory display is done via direct field access elsewhere

  An `operator<<` that omits the item list means every display site that needs to show item names must reimplement the iteration logic itself, scattering display concerns across the codebase instead of centralising them in the operator.

  ```cpp
  // Inventory.cpp:154 — prints count only, not the items
  std::ostream& operator<<(std::ostream& os, const Inventory& inventory)
  {
      os << "Inventory size: " << inventory.items.size();
      return os;
  }
  ```

**Operator Overloading — 6 / 10**
- `operator==` on Item correctly omits `amount` to support stacking in `addItem()` — a deliberate design choice
- `operator<<` on Item prints name, quantity, and cost but omits the type string (−1)

  Omitting the type string means a player looking at their inventory cannot distinguish a Potion from a material without already knowing the item names — the operator is incomplete as a display tool.

  ```cpp
  // Item.cpp:76 — no type field in the output
  std::ostream& operator<<(std::ostream& os, const Item& item)
  {
      os << item.name << " x" << item.amount << " gold:" << item.value;
      return os;
  }
  // "small Hp potion x1 gold:15" — type (Potion) never shown
  ```

- `operator<<` on Inventory prints only the item count, not the items themselves (−1)
- No bonus overloads (−2)

  Two additional points were available for any operator that fits naturally in your code — `operator+=` for healing, `operator-=` for damage, `operator<` for comparing item values, or `operator+` for merging inventories are all common choices in an RPG.

**Heap / Dynamic Memory — 10 / 10**
- STL-only mode; no raw pointers anywhere. Inventory uses `vector<Item>`; all objects in Fight::start() are stack-allocated. `extern const` Item globals use static storage. Rule of Zero applied correctly throughout — no memory leaks possible.

**Inheritance — 0 / 10**
- Not used. Each `EnemyProfile` wraps a `Character` by value and a fixed `intentLoop` — making `Character` (or a new `Enemy` class) the base with `RabidWolf`, `Ghoul`, `RedCultist`, and `RedDeath` as subclasses each overriding a virtual `getNextIntent()` would eliminate the parallel struct-and-vector pattern and let `Fight::start()` call through a single polymorphic interface.
