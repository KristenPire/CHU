## Overall

A build-choice RPG (Berserker vs Tank) with safe/dangerous routes each round, a two-drop loot system where you pick one and lose the other, and a three-phase boss — each run genuinely plays differently. The code is split across six focused game source files and uses two independent inheritance hierarchies, one for game roles and one for attack resolution, with runtime polymorphism exercised every combat turn. The main rough spots are a duplicated helper and an informal out-parameter pattern.

**Clean Code — 36 / 40**
- Excellent decomposition: `runOneRound()` (20 lines), `giveDropChoice()` (20 lines), `runBossPhase()` (13 lines) — all well-sized
- Operator overloads (`+=` for heal, `-=` for damage) are actually used in combat code, not just declared
- **`fightEnemy()` length** (−2) — 84 lines with display and combat interleaved; three internal lambdas add local structure but the function is still long; lambdas could be extracted as named helpers

  A function that mixes rendering, input, and combat resolution is harder to test, debug, and extend than one that delegates each concern to a focused helper.

  ```cpp

      int damage = doPlayerBasicAttack(m_player, atkBonusThisBattle, enemy);
      std::cout << "You dealt " << damage << " damage.\n";
  };
  auto showEnemyHpSnapshot = [&]() { ... };
  auto runEnemyTurn = [&]() { ... };
  ```

- **`computeRawDamage` duplicated** (−2) — defined identically in both `GameActions.cpp` and `GameCombat.cpp` anonymous namespaces; DRY violation that should be in a shared utility header

  When the same function exists in two files, a bug fix or rule change (e.g., changing the minimum damage floor) must be applied in both places — it is easy to update one and forget the other.

  ```cpp
  // GameActions.cpp:7 — first definition
  int computeRawDamage(int atk, int def) {
      int damage = atk - def;
      if (damage < 1) { damage = 1; }
      return damage;
  }
  // GameCombat.cpp:9 — identical definition in a separate anonymous namespace
  ```

**Operator Overloading — 9 / 10**
- `operator<<` on Character, `operator==` and `operator<<` on Item, `operator<<` on Inventory — all strong
- **`operator<<` on Item** (−1) — prints name and value but omits the type string (Weapon/Potion/Armor)

  When an Item is streamed (e.g., in the loot choice display), the reader sees `"small_potion(value=18)"` with no indication of what type of item it is, which makes the inventory less readable.

  ```cpp
  // Item.cpp:45 — operator<< outputs name and value only
  std::ostream& operator<<(std::ostream& os, const Item& item)
  {
      os << item.m_name;
      os << "(value=";
      os << item.m_value;
      os << ")";
      return os;
  }
  ```

- **Bonus overloads** (+2) — `Character::operator+=` (heal) and `Character::operator-=` (damage) both actively used in combat; `Item::operator!=` also defined

**Heap / Dynamic Memory — 10 / 10**
- STL-only mode; no raw pointers in any class. The `EnemyAttackResolver` polymorphism uses `std::make_unique<NormalEnemyAttackResolver>()` and `std::make_unique<BossEnemyAttackResolver>()` — idiomatic RAII, automatically destroyed at end of `fightEnemy()`. No memory leaks possible.

**Inheritance — 10 / 10**
- Two independent hierarchies: `Character → Hero / Enemy` (roleTag() overridden, used polymorphically in `operator<<`) and abstract `EnemyAttackResolver → NormalEnemyAttackResolver / BossEnemyAttackResolver` (factory via `make_unique`, pure virtual `resolve()` dispatched every combat turn)
- Virtual destructors on both base classes; `override` used correctly throughout; no object slicing
