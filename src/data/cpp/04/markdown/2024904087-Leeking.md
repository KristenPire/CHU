- **Rule of Three violated** (−4) — Character stores Weapon* with a destructor but no copy ctor/assign; Game stores Character* and vector<Character*> with a destructor but no copy ctor/assign — double-free UB if either is copied

  When a class has a destructor that frees owned pointers but no copy constructor or copy-assignment, copying the object causes two instances to own the same pointer — both will call `delete` on it, which is undefined behavior and typically crashes at runtime.

  ```cpp
  // Character.cpp:10-12 — destructor deletes weapon, but no copy ctor or copy-assign defined
  Character::~Character() {
      if (weapon) delete weapon;
  }
  // Game.cpp:12-16 — same violation: destructor deletes player and enemies, no copy ctor/assign
  Game::~Game() {
      if (player) delete player;
      for (auto* enemy : enemies) { delete enemy; }
  }
  ```

- **Naming inconsistencies** (−4) — no trailing underscore, getHp() vs getATK() inconsistency, hasItems() instead of isEmpty(), heal(-damage) as damage mechanism inverts semantics, public member access instead of getters

  Mixing naming styles (`getHp` vs `getATK`) and inverted semantics (`heal(-damage)` to apply damage) force readers to stop and reason about each call rather than reading the code fluently.

  ```cpp
  // Character.cpp:28 — heal() used with a negative argument to apply damage
  target->heal(-totalDamage);
  // heal() does not check for negative values; this works by accident, not by design
  // Separately: getHp() (lowercase 'p') vs getATK() (uppercase) — inconsistent convention
  ```

- **Style issues** (−4) — duplicate #include in Character.cpp, system("chcp 65001") and system("pause") non-portable calls, Item/Inventory entirely dead code

  A duplicate `#include` at the top of a file is a copy-paste artifact that, while harmless with include guards, signals the file was assembled without review; `system()` calls for encoding and pause are Windows-only and will fail silently or visibly on Linux and macOS.
