- **Rule of Three violation on Game** (−3) — Game has a destructor and raw `Character* enemy_` pointer but no copy constructor or copy-assignment; structurally unsafe if Game were ever copied

  A class that has a destructor but no copy constructor allows the compiler to generate a shallow-copy constructor — two Game objects would share the same `enemy_` pointer and both would delete it on destruction.

  ```cpp
  // src/Game.cpp:30-32 — destructor deletes enemy_
  Game::~Game() {
      delete enemy_;
  }
  // src/Game.hh — no copy constructor or copy-assignment declared
  // Character* enemy_  is a raw owning pointer — Rule of Three violated
  ```

- **Magic numbers in combat** (−2) — `rand() % 8` for crit chance, `rand() % 3` for stat selection, `rand() % 40 + 20` for gold reward — should be named constants

  A reader seeing `rand() % 8` has no idea whether 12.5% was a deliberate design choice or an arbitrary number — a named constant like `CRIT_DENOMINATOR = 8` documents the intent directly.

  ```cpp
  // src/GameActions.cpp:67 — magic 8 for crit chance
  bool critical = (rand() % 8 == 0);

  // src/GameActions.cpp:131 — magic numbers for gold range
  int goldReward = 20 + rand() % 40;
  ```

**Heap / Dynamic Memory — 8 / 10**
- `enemy_` pointer carefully managed: deleted and nulled before every reallocation, in `clearEnemy()`, in `resetGame()`, and in the destructor; no dangling pointers identified
- **Rule of Three violated on Game** (−2) — destructor present but no copy constructor or copy-assignment; double-free risk if Game were ever copied

  Even if Game is never actually copied in the current program, a class that owns a raw pointer must define all three of the destructor, copy constructor, and copy-assignment — otherwise a future refactor that copies Game will silently produce a double-free crash.

  ```cpp
  // src/Game.cpp:30-32 — destructor frees enemy_
  Game::~Game() {
      delete enemy_;
  }
  // No Game(const Game&) and no Game& operator=(const Game&) anywhere
  // Compiler-generated copy ctor would copy enemy_ pointer — shared ownership
  ```

**Inheritance — 0 / 10**
- Not used. All five enemies including the Demon Lord are plain `Character` objects assigned to `enemy_`. A `Character` base with an `Enemy` subclass and a `Boss` subclass overriding a virtual `onTurn(Character&)` would have let the Demon Lord execute unique phase behavior through the same combat dispatch that handles regular enemies, rather than requiring separate branching in `run()`.

## Bonus

**Bonus score: 7 / 10**

The freedom to move between four named areas instead of walking a linear corridor is a meaningful design choice — it lets you decide when you're ready to push into harder zones, and ducking back to the safe zone when things get rough feels like a real option rather than a cheat. The gold-shop loop (fight → collect → buy → push further) is simple but genuinely satisfying.

The heavy attack at 70% accuracy adds a real decision to every turn, and the permanent stat-up after each fight makes the grind feel like it's going somewhere.

**Clean Code note:** The `GameConfig.hh` for platform-specific color constants and the clean method decomposition (`normalAttack`, `heavyAttack`, `enemyTurn`, `checkBattleEnd`, `giveReward`, `openShop`, `moveToRoom`) show good organizational instincts. The trailing-underscore member convention is applied consistently. The main structural issue is `run()` at roughly 78 lines — the game state machine loop with both combat dispatch and area navigation lives inline there, and it would be much cleaner extracted into a `processGameTurn()` helper. Named constants for the magic numbers scattered through `GameActions.cpp` (combat probabilities, gold ranges, stat amounts) would be the other main improvement.
